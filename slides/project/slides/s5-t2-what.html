What is MCP?

MCP — the Model Context Protocol — is an open standard for how a client exposes tools, data and prompts to a model. It gives tools a common wire format, so any MCP-speaking client can use any MCP server.

A server

Advertises tools. Databricks hosts one per schema, with nothing for you to deploy.

tools/list

Ask what tools exist. The answer depends on who is asking.

tools/call

Invoke one by name with arguments. The server executes and returns a result.

Managed endpoint

/api/2.0/mcp/functions/{catalog}/{schema}

Your schema is already a server

Register functions in a Unity Catalog schema and that schema's MCP endpoint serves them as tools. No gateway, no adapter, no deployment step.

The analogy

USB for tools. The socket is standard, so the device and the host do not need to know each other in advance.

Expand the acronym and define it properly, because MCP is new enough that half the room will have heard the name and not the definition. It is a protocol — a wire format for advertising and invoking tools — not a product and not a Databricks feature. The thing that surprises people is the white panel. There is no MCP server to build. Register functions in a Unity Catalog schema, and that schema has an endpoint which serves them as MCP tools. The catalog is the registry. Keep the two verbs straight because they carry the next two slides: tools/list asks what exists, tools/call invokes one. The interesting half is tools/list, because the answer is not fixed — it depends on the identity asking. Analogy: USB. The value is not any individual device; it is that the socket is standard, so a host and a device that have never met can work together. Likely question: "Do I need MCP if I am writing the agent myself?" Not strictly — you can read the catalog directly, as the previous lab did. MCP matters when the client is not yours: a desktop assistant, another team's agent, a tool you have not evaluated yet. Timing: 3 minutes.
