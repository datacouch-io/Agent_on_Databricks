How the managed MCP server works

1 · Register

functions in a UC schema

2 · Endpoint exists

/api/2.0/mcp/functions/{cat}/{sch}

3 · Client authenticates

as a user or a service principal

4 · tools/list

filtered by that identity's grants

5 · tools/call

executed with definer's rights

Step 2 needs no deployment

The endpoint is derived from the schema name. There is no server process, no container and no uptime of yours involved.

Step 4 is the interesting one

Discovery is identity-filtered. A client without EXECUTE does not get a refusal — the tool is simply absent from the list.

Step 5 keeps the boundary

The function body runs as its owner, so the client needs no access to the underlying tables.

One schema, one surface

Group tools by audience: a schema per agent role is a clean pattern.

Also served: Genie Agents and indexes

Managed MCP covers more than functions — the same identity rules apply.

Five boxes and the middle one is the slide. Everything else supports it. Step two: there is nothing to deploy. People keep asking where the server runs, because every other MCP server they have met was a process someone started. Here the endpoint is a function of the schema name, and your operational burden is zero. Step four is the design worth admiring. Discovery is filtered by the caller's grants. That is subtly but importantly better than checking at call time: a tool the client cannot use does not appear in the list, so the model never considers it, never attempts it, and never produces an explanation about why it could not. There is nothing to argue with and nothing to jailbreak toward. Step five closes the loop with definer's rights from earlier. The client gets EXECUTE on a function and no access to the tables it reads. Mention the last panel briefly so the room knows the surface is wider than functions — Genie Agents and vector indexes are served the same way, under the same identity rules.
