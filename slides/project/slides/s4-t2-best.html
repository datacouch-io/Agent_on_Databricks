Curating a Genie Agent — do and don't

Do

Write About first. State the grain: “one row per order” prevents a lot of nonsense.

Instructions for rules, examples for shapes. Joins and date conventions want SQL.

Document the exclusions nobody wrote down — test accounts, internal orders, migrated rows.

Keep instructions and examples in version control and apply them through the API.

Review knowledge-mining suggestions one by one before accepting.

Add a benchmark case every time you add an instruction, so the fix is measured.

Don't

Don't give a space more tables than it needs. Scope is the cheapest quality control you have.

Don't describe a join in prose and hope. Write the example query.

Don't write instructions as etiquette. “Be careful with revenue” does nothing.

Don't let the console be the source of truth for rules that govern reported numbers.

Don't accept mined suggestions in bulk — your query history has bad habits in it.

Don't assume a plausible number is right. It executed; that is all you know.

The third “don't” is the most common mistake. Instructions are read as context, not obeyed as policy — so they must be specific and checkable. “Revenue excludes orders with status cancelled” works. “Be accurate about revenue” is a wish.

86

Close the curation topic here. Three lines are worth saying aloud. The callout first. People write instructions as if briefing a careful colleague — "be careful with revenue figures", "remember that data quality varies". None of that changes a query. An instruction earns its place only if you could check whether the generated SQL honoured it. Specific, checkable, and ideally paired with a benchmark case. "Don't give a space more tables than it needs" is the cheapest quality lever in the product and it feels wrong to people who want one space for everything. Narrow spaces answer their questions better. Build several. "Add a benchmark case every time you add an instruction" is the practice that makes curation cumulative rather than anecdotal. Without it you have a space that someone improved once and nobody can prove still works. The last "don't" is the session's closing note and the course's theme again: the query ran, so you have a number. Whether it is the right number is a separate question needing a separate instrument — which is the next topic. Likely question: "Who owns these entries?" The people who own the metric definitions. This is a governance artefact that happens to be consumed by a model, and putting it in the ML team's backlog is how it goes stale. Timing: 3 minutes.
