Three span types carry the meaning

AGENT  the whole turn
TOOL    one call and its arguments
RETRIEVER  what came back, and from where

SELECT request_id, status.code,
       execution_duration
FROM cat.sch.mlflow_experiment_trace_spans
WHERE span_type = 'TOOL'

Not status_code. Trace tables are OpenTelemetry — status is a struct. The obvious query fails with UNRESOLVED_COLUMN.

Traces in a catalog are an ordinary table. Latency by tool, retrieval hit rate, which document grounded which answer — all of it is SQL.

A screenshot of a trace is a debugging aid. A table of traces is an operations practice.

Lab 3B. One decorator per function, one destination, and the agent becomes observable. Show the trace UI first — the nested spans, the arguments, the retrieved chunks — because it is immediately legible. Then move straight to the SQL, because the UI is where you look at one interaction and the table is where you learn something about a thousand. Span types are not decoration. Setting span_type correctly is what makes RETRIEVER spans show retrieved documents in the UI and what lets MLflow's built-in retrieval scorers find your retrieval step in Session 6. Mislabel it and the evaluation silently has nothing to grade. The gotcha is worth the thirty seconds: everyone writes status_code, and the query fails. These are OpenTelemetry spans, so it is status.code. Cheaper to hear it here than to debug it in a lab. Expected question: "Does tracing cost latency?" The spans are written asynchronously; the overhead is small and you can sample in production. The cost of not having them is an agent you can only describe anecdotally. Timing: 5 minutes.
