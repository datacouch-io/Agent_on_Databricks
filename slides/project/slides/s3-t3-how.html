Three decisions encoded in that call

Which column is embedded — only that text is searchable.

Which columns are carried — anything you want to filter on must be in the index.

How it stays current — triggered, or continuous and warm.

Creation is asynchronous

The call returns before the index is ready. The lab polls until status is ONLINE.

Adding a document

Insert into the Delta table, trigger a sync, search again. No other step.

Walk the five boxes, then spend the time on the right-hand panel, because those three decisions are the ones you cannot easily change later. Only the column you name gets embedded. If your searchable meaning lives in two columns — a title and a body — concatenate them upstream in the table or you will be searching half your corpus. The second decision is the one people discover painfully: filters can only use columns the index carries. Decide your filter dimensions when you create the index, not when you first need them. The asynchronous note matters for anyone scripting this. create returns immediately and the index is not usable yet; the lab polls status until ONLINE and prints progress. Without the wait loop the first search fails confusingly. Demonstrate the add-a-document cycle live if time allows: insert a row, trigger the sync, search for its content. Three statements, and it is the whole document lifecycle. That is the moment the "subscription, not a copy" idea becomes concrete. Likely question: "Can I use my own embeddings?" Yes — a self-managed index takes a vector column you compute. You then own the embedding job, which is exactly the thing managed embeddings removed. Timing: 4 minutes.
