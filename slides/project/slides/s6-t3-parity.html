Deploying what you measured

The version you evaluated is not automatically the version you deployed

Your agent is written twice — the notebook you evaluated, and the file that serves traffic. Nothing warns you when they stop agreeing.

1 · Configuration

Read the constants out of both files — prompt, k, max tokens, tool names — and fail on any difference. Parse the literals; do not import.

2 · Version

Read served_entities back off the endpoint and assert it is the version this run registered. Being given a version is not serving it.

3 · Behaviour

Re-run the same cases, same scorers, through the endpoint. Different process, different identity — source parity is not behaviour parity.

What this course actually shipped

Our deployed agent had no tool loop at all — no order lookup, a shortened prompt. Case 4 asked it to look up an order, and the lab quoted the notebook’s score for it.

The trap in the deploy cell

It skips deployment when the endpoint already exists. Change the agent, re-run, and a new version is logged while the old one keeps serving.

The evaluation you can defend is the one you ran against the endpoint, at the version the endpoint is serving.

Session 6 has been about distrusting the measurement. This is the same habit pointed at the deployment step. The argument in one line: you evaluated an object in a notebook, and then you shipped a different object. Everything you can say about quality attaches to the first one. Walk the three checks and note that they get progressively more expensive and progressively more convincing. Constants are free and catch most drift. The version assertion is one API call and catches the thing nobody expects - a successful deploy that changed nothing. Re-running the suite costs real minutes and is the only one that catches behavioural difference. The admission on the left is worth making out loud. This is our lab, it shipped that way, and the parity check is what we added after a reviewer found it. A failure you can name is worth more than a principle you assert. Expected question: "Why not just import the notebook agent into the serving file?" Because a serving container has no SparkSession, so the order lookup has to reach the same data a different way - through the Unity Catalog function. Same contract, different transport.
