How an evaluation run is assembled

1 · Dataset

inputs plus expectations, versioned

2 · Predict fn

your agent, wrapped as a callable

3 · Scorers

built-in, plus your own

4 · mlflow.genai.evaluate

runs every row, scores every output

5 · Results table

one row per case, per scorer

results = mlflow.genai.evaluate(
    data=eval_df,
    predict_fn=run_agent,
    scorers=[
        Correctness(),
        RelevanceToQuery(),
        Safety(),
        Guidelines(name="follows_expectations",
                     guidelines=RULES),
    ],
)

Where the results actually live

Columns are flat: <scorer>/value and <scorer>/rationale. Not nested assessment objects — which is where our first analysis script found nothing and reported no failures at all.

Traces are captured too

Each evaluated run produces a trace, so you can see which tools ran per case.

Scorers are composable

Built-ins for generic qualities, Guidelines for your own rules in prose.

The call itself is four arguments and does not need much explanation. Spend the time on the right-hand panel, because it is a real trap. The results come back with flat columns — scorer-slash-value and scorer-slash-rationale. Our first rationale-extraction script assumed nested assessment dictionaries, found nothing matching, and concluded there were no failures to inspect. It was wrong, and it was wrong in the most dangerous direction: it reported clean. That is the second broken instrument in two slides, and we are only at the beginning of the session. The habit to build is to print the columns before you trust any script that reads them. Mention that traces are captured per evaluated case. That matters because a failing score plus its trace tells you whether the problem was retrieval, tool selection or generation — which is the four-way ambiguity from Session 3, now resolvable. Likely question: "Can I run this in a job on a schedule?" Yes, and you should once the suite is stable. Treat it as a test run on new model versions and new data. Timing: 4 minutes.
