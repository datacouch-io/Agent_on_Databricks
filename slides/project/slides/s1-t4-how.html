How memory works: short-term, long-term, and state

Short-term

The messages list for this conversation. Free, automatic, and grows without limit unless you act.

Long-term

Facts that outlive the conversation — preferences, prior tickets. A store you read from and write to deliberately.

Working state

Scratch values the loop carries but the model need not re-read every turn: ids, counters, partial results.

Summarisation

Replace older turns with a compact summary once the conversation passes a threshold.

Eviction

Drop tool output the next step cannot use. The cheapest technique and the least used.

Long-term memory is retrieval

There is no special mechanism. You store facts, and you retrieve the relevant ones into context — which makes it the same engineering problem as Sessions 2 and 3.

The rule that prevents most incidents

Design tools to return decided answers, not raw data. One row with named columns, not a result set. A tool that can return fifty thousand rows is a context bomb with no error message.

Three kinds of memory, and the useful insight is that only one of them is automatic. Short-term memory is the messages list. You get it for free and it grows forever. Long-term memory is not a feature of the model at all — it is a store you write to and retrieve from, which means it is the retrieval problem from Session 2 wearing a different hat. Say that explicitly, because people expect long-term memory to be a toggle. Working state is the one that saves money. Not everything the loop needs has to be in the model's context. An order id you are carrying between steps can live in a Python variable; it does not need to be re-read by the model on every turn. Summarisation and eviction are the two controls for a long conversation. Summarisation is the better-known one and costs an extra model call. Eviction is nearly free and almost nobody does it: once a sub-task is done, its intermediate tool output is dead weight that you keep paying to re-send. The bottom bar is the practical rule and it connects to Session 1's best-practice list. Tools that return decided answers rather than raw data make most context problems disappear before they start. Likely question: "Should I summarise automatically at a token threshold?" Yes, with a threshold you choose and a summary you can inspect in the trace. Silent summarisation is a lovely source of baffling bugs. Timing: 4 minutes.
