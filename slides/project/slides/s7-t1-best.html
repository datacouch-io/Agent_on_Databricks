Multi-agent systems — do and don't

Do

Start with one agent. Split when you can name the reason: tools, identity, owner or model.

Trace the handoff payload as its own span. It is where the bugs live.

Let workers ask for what they are missing rather than answering regardless.

Describe workers as carefully as tools. Routing quality is description quality.

Bound the supervisor's loop. A tree of calls grows faster than a line.

Give each worker its own identity when their permissions genuinely differ.

Don't

Don't split for elegance. Two loops cost twice and add a new failure mode.

Don't assume OK spans mean a good answer — Lab 7A's failure is entirely green.

Don't give the supervisor domain tools “just for convenience”. It stops being a router.

Don't share mutable state between workers. Explicit handoffs, every time.

Don't let a framework hide the loop from you before you have built one.

Don't debug multi-agent systems without traces. You cannot guess which hop was wrong.

The one to take away: in a single agent, context loss is nearly impossible, because every tool result is in one messages list. Splitting buys focus and sells away shared context. Make sure you are getting something for it.

Close the topic with the callout rather than the lists, because it is the sentence that should survive the session. A single agent cannot easily lose context. Everything it learned is in one conversation, visible to every subsequent step. When you split, you replace that shared list with deliberate handoffs, and every handoff is an opportunity to omit something. That is a real trade, not a detail, and it is the reason "default to one agent" is good advice rather than conservatism. Two other lines worth the breath. "Don't give the supervisor domain tools just for convenience" is how supervisor-worker architectures rot — one shortcut and the supervisor is now a generalist agent with workers attached, which is the worst of both. And "don't let a framework hide the loop" is the justification for how this course is sequenced; by now the room has written the loop, so LangGraph is a convenience rather than a mystery. If there is time, ask the room which of the four reasons to split applies to a system they are actually planning. Most will find it is tool count, which is usually solvable by better tool descriptions first. Likely question: "When is parallel fan-out right?" When lookups are genuinely independent and you need them all — several data sources for one summary. Then parallelism is a latency win rather than a cost multiplier. Timing: 3 minutes.
