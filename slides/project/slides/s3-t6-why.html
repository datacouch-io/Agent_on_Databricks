Why the best agent is often no agent

What goes wrong

Teams build an agent for a task with a fixed shape because the task involves language. Four thousand documents become four thousand loops, each a fresh opportunity to improvise on a financial record, with no way to diff this month's run against last month's.

The engineering value

A SQL statement is schedulable, idempotent, diffable and auditable. It fails loudly, it runs in a pipeline, and its output is a table your existing tests can assert on.

Use AI Functions when

The task is per-row, the output schema is fixed, and volume is high.

Use an agent when

The next step depends on what the model just found. Session 1's test, unchanged.

Use both when

An agent calls a Unity Catalog function whose body is an AI Function. Perfectly ordinary.

Real scenario

“Classify every support ticket by product area” sounds like an agent task because it needs judgement. It is ai_classify over a column, in a scheduled pipeline, producing a table — which anything else in your warehouse can then join to.

Session 1 asked you to default to the smaller thing. AI Functions are what the smaller thing often looks like on Databricks.

Lead with the recognition: a task involving language is not automatically a task needing an agent. Judgement per row is not the same as decisions about control flow. Runtime-dependent control flow is an agent. The third panel prevents a false dichotomy and is worth saying, because it is a genuinely good pattern: a Unity Catalog function whose body calls an AI Function, exposed to an agent as a tool.
