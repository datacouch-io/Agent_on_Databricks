One question separates a workflow from an agent

Do you know the sequence of steps before you see the data?

YES → Workflow

Cheaper, testable, fails predictably

No — and does the next step depend on what the model finds?

YES → Agent

instructions · model · tools · state · a stopping condition

Reach for an agent when the control flow itself has to be decided at runtime — not because the problem involves an LLM.

Two of the four lab scenarios are workflows. If your group called three or four of them agents, you have found the bias this exercise exists to correct.

ADDED TOPIC — the outline says "when to use each" but offers no test. This is the test. Four words get used interchangeably and should not be. An LLM call turns input into output. A workflow is a sequence of steps you wrote. RAG is a specific workflow — retrieve, then generate. An agent is different in exactly one respect: the model decides what to do next, in a loop, until a stopping condition is met. Analogy: a workflow is a recipe. An agent is a cook who tastes and adjusts. The trap in Lab 1A is the invoice scenario — four thousand PDFs with varying layouts. "The layouts vary" feels like it needs reasoning. It needs a good extractor with a fixed output schema. Wrapping it in an agent multiplies your token cost by the loop count and gives you four thousand independent chances to do something surprising. Expected question: "What if I am not sure?" Default to the workflow. You can always promote it; you rarely demote an agent once it ships. Timing: 3 minutes.
