What is a tool?

A tool is a function the model may ask you to run, described to it as a JSON schema — a machine-readable description of a name, its arguments and their types.

Name

What the model refers to. get_order_status — a verb and an object, not tool_1.

Description

Prose telling the model when to use it. This is prompt text in a data structure.

Parameters

Typed arguments, each with its own description and an example value.

Implementation

Your Python function. The model never sees it — only the schema.

The model does not call anything

It returns a request: a name and a JSON blob of arguments. Your code decides whether to honour it. That gap is where every control in this course lives.

The analogy

A restaurant menu. The kitchen is not visible; the descriptions are all the diner has to go on. A vague menu produces the wrong order.

Define this carefully because the word "tool" is doing two jobs: the schema the model reads, and the function you wrote. Keeping them separate in your head prevents a lot of confusion later. The sentence to stress is in the first panel. A model never executes anything. It emits a name and a JSON object, and your loop chooses what to do with that. People new to this assume the model has some channel to the outside world; it does not, and that is why the gate in Session 1 can exist at all. The description field is the part engineers under-invest in. It is the only thing standing between your tool and the model picking a different one. Treat it as prompt text that happens to live in a schema: review it, test it, and rewrite it when the model keeps choosing wrong. Analogy: a menu. The diner cannot see the kitchen. "Soup" sells less than "slow-roasted tomato soup with basil", and "soup" also gets ordered by people who wanted something else. Likely question: "How many tools can a model handle?" Practically, a handful to a few dozen before selection quality degrades. Past that, group them behind a router or split the agent — which is Session 7. Timing: 3 minutes.
