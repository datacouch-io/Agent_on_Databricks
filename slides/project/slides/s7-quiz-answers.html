Session 7 — Operations, Multi-Agent Systems and Best Practices

Answers

1C, 2A, 3D, 4B  — and why the others fail.

1

C — The filter was an argument your code passed, not a property of the index

A managed assistant inherits your data, not your controls. It was never told about the filter because the filter never lived in the index.

This is the course's sharpest result and the Session 4 inheritance test applied to a product you did not write: if a new client appeared tomorrow, would your rule still hold?

2

A — When you can name the reason: tool count, differing identities, separate owners, or different models

Split when you can name which of the four applies. Tool selection degrades past a few dozen tools; a worker that may issue refunds and one that may not is a real identity boundary.

Splitting early multiplies latency and cost and adds a failure mode that did not exist: the supervisor routes correctly and passes incomplete context, so a worker answers confidently from half the question.

3

D — No decision — n = 3 supports neither conclusion; widen the probe set

Reading both columns turns a frightening number into a comparison. Three versus two is not a finding. “Not enough data” is a legitimate outcome and the hardest one to report.

Reverting on the raw number is the trap: the course's own canary write-up called a challenger a regression when the control column said otherwise. The 90% is not just safety — it is what makes the 10% readable.

4

B — The sum of source lag, index lag, semantic lag and cache lag

The sum, not the maximum. A table updated hourly, an index synced every six hours and a one-day response cache is a day and a half of lag.

Nobody agrees a target, so there is no definition of stale, so there is no alert — and the lag is first measured during the incident review for an agent that quoted a withdrawn policy.
