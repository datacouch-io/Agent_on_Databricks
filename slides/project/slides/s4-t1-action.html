Step 4 — before curation

SELECT sum(total_amount)
FROM orders
WHERE order_date >= ...

-> 184,220.00

Cancelled orders included.
No warning. No hedge.

Step 5 — after one instruction

SELECT sum(total_amount)
FROM orders
WHERE order_date >= ...
  AND status <> 'cancelled'

-> 171,905.00

The rule now travels to
every caller of this space.

This is a live demonstration, not a slide to read. The lab guide has a screenshot for every click, including creating the space from an empty workspace, so people can follow afterwards at their own pace. Lead with the failure. Create the space, add the two tables, ask for last month's revenue, and read the generated SQL aloud. It sums total_amount with a date filter. There is no status predicate. The number is wrong by the value of every cancelled order, and nothing in the answer suggests a problem — it is a clean figure with a clean query. Pause there and ask the room how they would have caught it. The usual answer is "we would have checked the SQL", which is exactly the point: that only works while a person reviews every question, which is not the deployment anyone is planning. Then add one instruction — revenue excludes orders with status cancelled — and ask again. The predicate appears. Two numbers on the screen, twelve thousand pounds apart, and the difference is one sentence of curation. Likely question: "Where did the second number come from being right?" It is right because someone wrote down the rule. Genie did not learn it and could not have inferred it; a cancelled order is a row with a value in a total column. Timing: 20 minutes of guided build.
