What is a runtime adapter?

A runtime adapter is the thin layer that supplies everything environment-specific — credentials, endpoints, configuration — so the agent itself contains none of it.

Credentials

A token or a workload identity, resolved from the environment. Never a literal in code.

Endpoints

Model host, index name, warehouse id. Values, not imports.

Configuration

MAX_STEPS, top-k, thresholds, the model name. One object, one place.

Clients

Constructed outside the agent and passed in. The agent receives, never imports.

Four runtimes, one agent

A laptop with a profile, a notebook with an attached identity, a job with a service principal, a serving endpoint with its declared resources. All four hand the same agent a configured client.

The analogy

A kettle and a plug adapter. The kettle is identical in every country; the adapter is the only part that knows where it is.

This closes the gap left by Session 2's retrieval seam: retrieval was only one of the things that vary between environments. Walk the four cards as four things that must never appear inside the agent. Credentials are the obvious one. Endpoints are the one people leave inline. Configuration is the one that quietly spreads — a top-k here, a threshold there — until tuning requires reading the whole codebase. Clients are the subtle one: the agent should receive a configured client, not construct one, because constructing it means knowing which vendor you are on. The white panel is the test. The same agent has to run in four places over its life: a laptop, a notebook, a scheduled job, and a serving endpoint. Each resolves identity differently. If the agent itself knows any of that, it has four code paths wearing one name. Analogy: the kettle and the plug adapter. Likely question: "Is this not over-engineering for a prototype?" The adapter is about ten lines. The cost of retrofitting it is a day, usually on the morning you need to deploy, which is the worst possible morning. Timing: 3 minutes.
