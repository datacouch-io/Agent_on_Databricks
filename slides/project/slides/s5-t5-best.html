Tools, errors and approval — do and don't

Do

Return failures as tool messages the model can read and act on.

Classify transient versus permanent before retrying anything.

Validate business constraints in code, even when types are validated by the engine.

Gate irreversible actions on the argument, not on context you expect it to match.

Make tools idempotent where you can — a retried refund should not pay twice.

Log the refusal, not just the success. A gate that fires silently teaches you nothing.

Don't

Don't let exceptions escape the tool boundary. A stack trace is not an answer.

Don't retry a validation error. It will fail the same way, for money.

Don't return raw result sets on success or raw tracebacks on failure.

Don't put the approval rule only in the prompt. Session 1 settled this.

Don't assume the model will not retry a failed call with slightly different arguments. It will.

Don't swallow a failure silently and return an empty result. The agent will treat it as “none exist”.

The last “don't” is the nastiest bug in this family. A tool that catches an exception and returns an empty list turns an outage into a confident, wrong answer: “You have no orders with us.” Empty and broken must not look the same.

Close Session 5's extended material here, and lead with the callout because it is the bug people have shipped without knowing. A tool wraps its body in a try/except, catches a connection failure, and returns an empty list because that felt safe. The agent receives zero results and does exactly what it should with zero results: it tells the customer they have no orders. The database was down. Nothing errored anywhere in your system and the answer was confidently false. Empty and broken must not look the same. Return a failure the model can distinguish, and the agent will say it is having trouble reaching the order system rather than inventing a fact about the customer. Two others worth saying. Idempotency matters more in agents than in ordinary services, because the model may retry a call it believes failed — so a refund tool that pays twice is not a theoretical concern. And logging refusals is how you learn whether your gate threshold is sensible; a gate that only logs successes tells you nothing about how often it fires or why. Likely question: "How do I make a refund idempotent?" An idempotency key derived from the order and the request, checked in the function body. Standard payments practice, and it applies unchanged.
