Definer's rights

A UC function runs as its owner. The caller needs EXECUTE on the function, not SELECT on the table behind it.

You did not write a permission check. You wrote a GRANT — and every client of that schema is bound by it, including the ones you will never see.

Lab 5B is the cleanest demonstration in the course, and it takes three minutes to run. One agent. One notebook. Two tokens. Run it as the full principal and the refund goes through. Swap the token, change nothing else, and the agent degrades gracefully: it looks up the order, quotes the policy, and tells the customer a human will handle the payment. Draw out why that is better than a refusal. The restricted agent is not fighting its instructions — it genuinely has two tools. tools/list returned two. The model cannot be talked into calling something it was never shown. Compare that with a system prompt saying "do not issue refunds over fifty pounds", which is a request to a text generator. Definer's rights is the part people miss. The function runs as its owner, so you grant EXECUTE on the function and never SELECT on the table. The agent can look up one order by id and cannot read the orders table. That is the principle of least privilege expressed as a function signature. Expected question: "How do I do per-end-user permissions, not per-agent?" On-behalf-of-user authentication — the agent acts as the signed-in person and sees exactly their tools.
