How to reduce latency, in order of safety

1 · Stream

First token immediately. Does not change real latency; changes the experience entirely.

2 · Parallelise

Independent tool calls in one turn should run concurrently. Often the biggest real win.

3 · Shrink input

Time to first token tracks input length. The context work from Session 1, again.

4 · Fix the slow tool

Read span durations. It is usually one tool, and usually not the model.

5 · Cut steps

Coarser tools and clearer descriptions. Two steps instead of four halves the wait.

6 · Change model

Last. Measure quality at the same time, or you are guessing.

-- where the time actually goes
SELECT span_type, name,
       count(*) AS calls,
       percentile(execution_duration, 0.95) AS p95
FROM cat.sch.mlflow_experiment_trace_spans
GROUP BY span_type, name
ORDER BY p95 DESC

Six techniques, ordered by how little they can break. Streaming is first because it changes nothing real and changes the experience completely. The user sees a first token quickly and stops wondering whether it is working. If you do one thing, do this. Parallelism is second and it is usually the largest genuine win, because the loop can return several tool calls in one turn and most implementations execute them in sequence out of habit. Shrinking input is third and it is the context work from Session 1 arriving again — time to first token tracks input length. Fixing the slow tool is fourth, and the query on this slide is how you find it. Run it before optimising anything. Almost every team that guesses blames the model, and almost every time it is one tool doing something sequential or unindexed. Cutting steps is fifth: coarser tools and clearer descriptions. Model change is last, for the same reason as on the cost slide — widest blast radius, easiest to justify badly. The right-hand panel is the point to land: this needs no new instrumentation.
