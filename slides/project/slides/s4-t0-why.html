Why Genie sits beside your agents, not inside them

What goes wrong if you build this yourself

A model with your schema in the prompt writes plausible SQL and knows no business rules. It will sum a column called total_amount and call it revenue. You then build the missing pieces: scope limits, stored definitions, worked examples, a regression suite, and somewhere governed to keep them.

The engineering value

Those pieces are the product. A Genie Agent gives curation a governed home, and the same curation then serves Genie One, Genie Code and any agent that calls it.

For people

Genie One answers business questions directly, with the SQL visible.

For agents

Your agent gets one tool — ask a question — instead of a run_sql tool.

For engineers

Genie Code works where you already are: notebooks, SQL editor, pipelines.

Real scenario

A finance team asks for last quarter's revenue. A hand-built text-to-SQL prompt returns a number including cancelled orders — close enough to look right, wrong enough to misreport, and the only check available is whether the query executed.

The hard part of natural-language analytics was never SQL generation. It is writing down the definitions your organisation argues about, somewhere a machine can read them.

The middle panel is the architectural point and it sets up Lab 4B. Giving an agent a run_sql tool is powerful and indefensible: it can query anything its principal can read, with no business rules applied. Giving it a Genie Agent is less powerful and far more defensible, because the curation travels with the data. The closing line is the real argument and it is not a software argument. Most organisations have no agreed definition of revenue, active customer or churn. Genie forces that conversation and then stores the answer. Several teams find the conversation worth more than the tool. Likely question: "Should we use semantic views instead?" Use both — curated views plus a curated Genie Agent.
