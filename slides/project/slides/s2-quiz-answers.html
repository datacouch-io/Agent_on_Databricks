Session 2 — Platform-Agnostic Agent Implementation

Answers

1B, 2C, 3D, 4A  — and why the others fail.

1

B — Vendor imports and vendor-specific parameters

Vendor imports live on one side of the seam. core.py imports json, os and the model client — and the lab asserts on those imports.

Leaking a vendor parameter through the signature “just because one backend needs it” is the named failure. The fixed shape is the contract; each retriever converts to it internally.

2

C — Rewriting the tool description

Rewriting a description costs nothing, ships instantly, and needs no retraining, no fine-tuning and no new infrastructure. The description is prompt text in a data structure.

Both failure modes — wrong tool picked, plausible arguments invented — look like model stupidity in a demo and turn out to be a one-line description doing no work.

3

D — It needs the policy and the customer's actual purchase — and it will guess the second

Two facts are needed: what was bought and when, and what the policy permits. A guessed purchase date produces a confident, wrong answer.

Structured retrieval is correct-or-absent; unstructured is plausible-with-a-score. The model should pick the path — there is no if 'order' in question anywhere in the lab.

4

A — Each runtime runs as a different principal, and the failure appears far from its cause

A notebook runs as you, a job as a service principal, an endpoint as itself — and it must have declared its resources at log time.

Retrieval ports cleanly and model calls port cleanly; identity does not. Once identity is an input rather than an assumption, moving runtimes becomes a configuration change.
