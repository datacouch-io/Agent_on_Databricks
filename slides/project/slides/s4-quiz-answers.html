Session 4 — Databricks Genie

Answers

1D, 2A, 3B, 4C  — and why the others fail.

1

D — It sums every row — including cancelled orders — and is confidently wrong

The model sees column names and types. It does not know that status has a value meaning the order never happened. It will make a choice, and the SQL will run.

An empty space is a worse analyst than your junior. Every instruction you add is a defect class removed permanently, for every caller.

2

A — The result sets produced by running both queries

Both are executed and the rows compared — so a correct answer written differently still passes. That is what makes it a regression test for a non-deterministic component.

Comparing query text would fail every correct query that happens to use a different join order or alias, making the suite useless as a measure of curation.

3

B — The rule lives where the query executes, so every caller inherits it; the filter protected only that caller

A control's reach is decided by its location, not by its correctness. One was inherited; the other was a property of one caller.

This is the same inheritance test Session 7 applies to Agent Bricks — where a managed assistant read the same index and disclosed DOC-006.

4

C — Candidate snippets are gated by Unity Catalog permissions on the assets they came from

Retrieval is permission-gated at step 2 — the security boundary. Nothing you cannot see can reach your answer.

Authority ranking (source, usage, freshness) is the quality lever at step 3, not the security boundary. Confusing the two is how a demo becomes an incident.
