What is the retrieval seam?

The retrieval seam is the single function signature through which your agent asks for documents — chosen so that nothing behind it leaks into the agent's own code.

The contract

search_docs(query, k) → a list of {doc_id, text, score}. That is all the agent knows.

Behind it

A dictionary, a keyword index, Databricks AI Search, or a product that does not exist yet.

The rule

Vendor imports live on one side of the seam. core.py imports json, os and the model client.

Why a function

Not a class hierarchy, not a framework. The smallest thing that can be swapped.

This is dependency inversion, nothing exotic

The agent depends on the shape of an answer, not on who produces it. The oldest idea in software design, applied to the fastest-moving layer of your stack.

The analogy

A light fitting. The lamp does not know whether the current comes from a wind turbine or a diesel generator — because the fitting is standard.

Name the idea plainly: this is dependency inversion. There is nothing novel in it, and saying so is reassuring rather than deflating — it means the architecture question has a known answer even though the components are new. What is new is how fast the thing behind the seam changes. Vector databases, embedding models, retrieval APIs and managed assistants are all moving quarterly. Code written against any specific one of them ages badly, and the labs in this course would be unrunnable in a year if they were not written this way. Stress the contract line. The agent knows it will get back a list of dictionaries with a doc id, some text and a score. It does not know whether a similarity search happened. Keeping that boundary honest is a discipline, not a one-time design: the temptation is always to pass one extra vendor-specific parameter through. Analogy: a standard light fitting. The lamp is indifferent to the generation source. Likely question: "Isn't this what LangChain's Retriever interface already is?" Yes — and understanding why that interface exists is the point.
