Why traces separate debugging from operating an agent

What goes wrong without them

An agent misbehaves in production and all you have is the final answer. You cannot tell whether retrieval returned nothing, the model picked the wrong tool, a tool failed and the model improvised around it, or the answer was right and the user was wrong. Four different fixes, no way to choose.

The engineering value

A trace tells you which of those happened, per interaction. A table of traces tells you how often each happens, which is the difference between anecdote and a work queue.

Latency by tool

Find the one slow tool dominating your p99 instead of blaming the model.

Retrieval hit rate

How often did search return nothing useful? That is a content gap, not a model fault.

Grounding audit

Which document produced this answer — and was the reader allowed to see it?

Real scenario

Support reports the agent “gets vague on returns questions”. One query over the spans shows retrieval returning a top score below 0.4 on those questions. The model was behaving correctly — it had nothing to work with. The fix was a missing policy document, not a prompt.

A screenshot of a trace is a debugging aid. A table of traces is an operations practice.

This is the argument for instrumenting before you need it, which is always a harder sell than instrumenting after. The four-way ambiguity in the first panel is the real experience of debugging an agent without traces, and naming all four possibilities makes the point better than any abstraction. The same bad answer has four causes and four different fixes, and the final text cannot distinguish them. The scenario is the best one in this session because it inverts the expected conclusion. "The agent is vague" sounds like a model or prompt problem, and the trace showed retrieval scores under 0.4 — there was no document. Nobody would have found that by rewriting the prompt, and plenty of teams spend a week trying. The closing line is the summary to leave up. One trace answers "what happened here". A table of traces answers "what is wrong with this system", and only the second one generates a work queue you can prioritise. Likely question: "What does tracing cost?" Spans are written asynchronously, so the latency impact is small, and you can sample in production. The cost of not having them is an agent you can only describe anecdotally — and in a regulated setting, one you cannot evidence at all. Timing: 4 minutes.
