Identity and governance — do and don't

Do

Use on-behalf-of-user for employee-facing assistants. Each person sees their own scope.

Use a service principal for unattended flows, with the smallest viable grant set.

Grant by application ID and keep a note of which principal is which.

Group tools into schemas by role, so a grant is one statement and not twelve.

Run your evaluation suite per identity — a graceful handoff is a correct answer.

Rehearse revocation. Know how fast you can remove a capability in an incident.

Don't

Don't expose a tool and forbid it in the prompt. Filter discovery instead.

Don't give an agent a human's personal token. It outlives the session and audits to the wrong party.

Don't share one service principal across agents with different risk profiles.

Don't grant by display name. Two principals can share one.

Don't treat a client-side check as a control — MCP means the client is a variable.

Don't let grants accumulate. Review what each principal can still do, on a schedule.

The second “don't” is the most common shortcut in a prototype and the hardest to unwind. An agent running on a person's token inherits everything that person can do, and every action in the audit log is attributed to them. Create the service principal on day one.

Close Session 5 with this. Three lines matter more than the rest. The callout first. Running an agent on a developer's personal access token is how every prototype starts, and it is worth stopping early. The agent inherits that person's entire access — which is almost certainly far wider than the agent needs — and the audit trail attributes every action to a human who was not involved. When the prototype quietly becomes production, you now have an unbounded identity you cannot safely remove because things depend on it. "Rehearse revocation" is the practice nobody has. Ask the room: if your agent started issuing wrong refunds right now, how long to take that capability away, and would you be sure it was gone everywhere? With grants the answer is seconds and yes. With code paths it is a deployment and probably. "Don't let grants accumulate" is the slow failure. Principals gain permissions for one-off reasons and never lose them, and two years later your restricted agent is not restricted. Likely question: "Who should own these grants?" The same people who own table grants. Agent permissions are data permissions, and splitting them across two teams is how they diverge. Timing: 3 minutes, then break.
