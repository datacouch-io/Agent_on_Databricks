Session 5 — Tools and Governance

Answers

1A, 2C, 3B, 4D  — and why the others fail.

1

A — The tool description the model reads when deciding whether to call it

Signature becomes the JSON schema, COMMENT becomes the description, GRANT becomes the access control. This is prompt engineering in DDL — review it like code.

Give every parameter an example value in its comment and malformed arguments largely stop.

2

C — Two tools — issue_refund simply does not appear

Discovery is identity-filtered. The restricted principal is not refused at call time — the tool never appears.

An absent tool cannot be argued for. Expose it and forbid it and you have created a negotiation, with a sentence in a prompt as the only thing between an insistent user and the capability.

3

B — EXECUTE on the function, and not SELECT on the table

The function runs as its owner, so the caller needs only EXECUTE. That is the point: a narrow, decided capability instead of access to the whole table.

Granting SELECT hands the agent everything the function was designed to narrow. Grant to the application ID, never the display name — display names are not unique.

4

D — A tool message describing the failure, classified as transient so a retry is justified

Report, don't crash: the model can then ask the user or try another route. Classify transient versus permanent before retrying — a timeout is not a ValueError.

Retrying a bad argument fails identically every time. An empty result silently teaches the model the data does not exist.
