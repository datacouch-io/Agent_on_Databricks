Session 3 — Data Grounding and Agent Construction

Answers

1C, 2D, 3A, 4B  — and why the others fail.

1

C — The primary key plus Change Data Feed, which tells the index what moved

Insert into the table, trigger a sync, search. Deletions and updates propagate because Change Data Feed tells the index what moved. There is no embedding job in your repository.

The classic RAG pipeline — chunk, embed, upsert, handle deletions, backfill — is a production service with on-call implications whose failure mode is silent staleness.

2

D — Because search ranks only what you gave it — if the answer is not a retrievable unit, nothing recovers it

No embedding model, no top-k and no reranker produces an answer that was never a retrievable unit. In Databricks your rows are your chunks — the table is the decision.

Too large: high scores, low usefulness, expensive context. Too small: the clause is retrieved without the condition that qualifies it, and the agent answers from half a rule.

3

A — You wrote status_code; these are OpenTelemetry spans, so it is status.code

Trace tables are OpenTelemetry: status is a struct. The obvious query fails, and this is the gotcha everyone hits.

An unset destination would produce no tables at all rather than a missing column. Spans are written asynchronously, but that yields missing rows, not an unresolved column.

4

B — An AI Function — ai_classify — called from SQL

Per-row task, fixed output schema, high volume. A SQL statement is schedulable, idempotent, diffable and auditable, and its output is a table your existing tests can assert on.

An agent gives you 4,000 loops, each a fresh opportunity to improvise, with no way to diff this month's run against last month's. The best agent is often no agent.
