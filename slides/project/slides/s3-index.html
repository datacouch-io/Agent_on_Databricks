Three decisions that bite later

Managed vs self-managed embeddings. Managed means you never run an embedding job — and never choose the model.

TRIGGERED vs CONTINUOUS. Triggered is cheap and stale. Continuous keeps a warm cluster.

Which columns to carry. Anything you want to filter on must be in the index.

index.similarity_search(
  query_text="laptop arrived smashed",
  columns=["doc_id", "text", "audience"],
  filters={"audience": "customer"},
  num_results=3,
)

That filter lives in the caller. Remember where you put it — in Session 7 something else calls this index and does not inherit it.

Lab 3A. The index build itself is about fifteen lines and one wait loop; the decisions around it are the content. Start with the subscription idea. You do not load documents into a vector database. You point an index at a Delta table with a primary key and Change Data Feed enabled, and the platform keeps it current. Insert a row, trigger a sync, search again — the new document is there and you wrote no pipeline. On the three decisions: managed embeddings are the right default and a real constraint. You trade model choice for never operating an embedding job. Self-managed is there when you need a domain-specific embedding model. The last box is a deliberate plant. We attach an audience column and filter on it in the caller, so internal-only documents never reach customer-facing answers. It works perfectly in this lab. In Session 7 an Agent Bricks Knowledge Assistant reads the same index, does not pass that filter, and discloses DOC-006. The control was never in the index — it was in our code. Where a control lives determines whether it is inherited. Expected question: "Should the filter be in the index instead?" You cannot filter an index into existence per-caller, but you can split indexes by audience, or put the rule in a Unity Catalog function that every caller must go through.
