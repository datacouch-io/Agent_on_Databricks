AI Search — do and don't

Do

Chunk upstream, in the table. Your rows are your chunks; get them right before indexing.

Carry every column you may filter on, even ones you do not need today.

Start with TRIGGERED on a schedule, and justify CONTINUOUS with a staleness requirement in hours.

Poll for ONLINE before the first search. Creation is asynchronous.

Test deletions, not just inserts. Retired documents are the common silent bug.

Put audience or tenant rules in a function every caller must use — not in one caller's arguments.

Don't

Don't index exact-lookup data. Embedding an order id finds similar ids, which is nonsense.

Don't assume a high score means relevant. Similarity search always returns its nearest row.

Don't skip the primary key or Change Data Feed and expect sync to work.

Don't return raw search results to the model unbounded — top-k exists for a reason.

Don't filter in the caller and call it a security control. The next caller will not do it.

Don't rebuild the index to add a document. Insert and sync.

The last pair on each side is the same lesson from two directions, and it is the one this course returns to most: a filter in your calling code protects your calls. In Session 7 an Agent Bricks assistant reads this very index without that filter and discloses an internal document.

Six and six again. Three are worth saying aloud. "Don't assume a high score means relevant" is the trap that produces hallucination-shaped bugs. A similarity search has no concept of "no good answer" — it returns the nearest rows it has, with scores, and a 0.72 on an irrelevant document looks identical to a 0.72 on the right one. If your corpus does not contain the answer, you will get three confident-looking passages anyway. Guard with a score floor and an instruction to say "not covered by policy".
