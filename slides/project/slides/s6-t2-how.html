How the built-in judges divide the work

RetrievalGroundedness

Is the answer supported by what was retrieved? The hallucination detector. No ground truth.

RelevanceToQuery

Does the answer address what was asked? Catches fluent, off-topic responses.

RetrievalRelevance

Were the retrieved documents relevant? Needs a RETRIEVER span to find.

Correctness

Right, against ground truth. Requires it — and penalises correct refusals.

RetrievalSufficiency

Did the context contain the facts needed? Requires ground truth.

ToolCallCorrectness

Did the agent call the right tools? Requires ground truth.

ToolCallEfficiency

Did it avoid redundant calls? No ground truth needed.

The built-in judges are the fastest route to a quality signal, and the list is longer than most people expect — ten standard judges plus seven that score whole conversations rather than single turns. The useful framing is which ones need ground truth, because that determines what you can run today. RetrievalGroundedness, RelevanceToQuery, RetrievalRelevance, ToolCallEfficiency, Safety and Guidelines need none — you can point them at production traces with no labels at all. Adopt RetrievalGroundedness first and say why: it answers "did the model make this up?" by comparing the answer against the retrieved context, with no labelling effort. That is a hallucination detector you can run on real traffic this week. Correctness is the one carrying the warning from the previous slide. It requires ground truth and it marks correct refusals down, because by its own definition the request was not fulfilled. The two tool-call judges are newer and worth knowing: they score whether the agent chose the right tools and whether it wasted calls — which is tool-selection quality as a number, and it is the thing your tool descriptions actually control. The multi-turn judges matter the moment you ship a conversational agent. UserFrustration in particular is a very direct production signal. Likely question: "Can I run these without writing code?"
