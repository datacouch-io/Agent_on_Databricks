How the loop works, one turn at a time

1 · Ask

model gets instructions, history and tool schemas

2 · Branch

text? done. tool calls? carry on

3 · Gate

check the arguments before anything runs

4 · Execute

call the function, with retry on transient failure

5 · Append

result goes back as a tool message

Step 2 is the only control structure

Everything an agent framework offers is scaffolding around this one branch. There is no second kind of decision.

Step 3 is where governance lives

The gate sees the arguments the model composed — before any side effect. This is the last honest place to say no.

Step 5 is why context grows

Tool output becomes prompt input. A tool that returns 50,000 rows does not fail; it poisons the next turn.

Retry, but only for transient failures

A timeout is worth retrying. A ValueError from bad arguments is not — retrying it just spends money to be wrong twice. The lab's call_with_retry distinguishes the two.

Loop back to step 1

The model now sees its own request and the result. That is what lets step two of a two-step answer be informed by step one.

Any check you want to be a control must happen in that window; anything earlier is a guess about what the model will do, and anything later is an incident report. Step five, because of the trap. Appending the tool result is what makes the loop work and also what makes an unbounded tool output dangerous. Nothing errors. The next prompt is just enormous, slow and expensive, and the model's attention is spread across fifty thousand rows of noise. Design tools to return small, decided answers. On retries: the distinction between transient and permanent failures is worth thirty seconds. A network timeout deserves a second attempt. A validation error means the model built the wrong arguments, and the fix is a clearer tool description, not another attempt. Likely question: "Can the model call several tools in one turn?"
